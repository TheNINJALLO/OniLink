# OniLink 0.1.5

OniLink 0.1.5 moves commercial tenant hosting into the owner-only main control plane. Providers can
connect Pterodactyl, create customers and plans, choose live free allocations, provision isolated
OniLink servers, and manage their lifecycle from one browser workflow. The locked BDS version,
Endstone version, OniForward protocol, and production-approved native profile are unchanged.

## Main-panel tenant hosting

- The new owner-only **Tenant Hosting** page stores the Pterodactyl connection server-side and
  returns only redacted key status to the browser.
- Pterodactyl customers, nodes, nests, eggs, and currently unassigned allocations are discovered
  through the Application API instead of requiring operators to copy numeric IDs.
- Providers can create normal Pterodactyl customer accounts and reusable memory, disk, CPU, backup,
  database, and maximum-player plans from OniLink.
- Provisioning creates one dedicated OniLink server per tenant, assigns exactly one primary
  allocation, sets the additional-allocation limit to zero, and generates tenant-specific setup and
  forwarding secrets.
- Each tenant receives a private handoff ZIP containing its one-time dashboard setup code and the
  matching `default.key` plus `onibridge.toml` for its BDS backend.
- Stable `onilink-tenant-<tenant>` external IDs let interrupted creates reconcile safely without
  creating a second server or replacing the saved handoff.
- Sync, retry, suspend, and restore controls keep routine lifecycle management in the same page.
  Permanent deletion remains deliberately outside this workflow.

## Security and persistence

- All hosting routes require the dashboard owner role; viewer, operator, and admin accounts are
  rejected by the server even though the browser also hides the page.
- The Pterodactyl Application API key, generated forwarding secrets, tenant records, and handoff
  ZIPs stay under `dashboard/hosting/` with owner-only POSIX permissions where supported.
- API responses, audit details, and support bundles do not expose the panel key or tenant forwarding
  keys.
- The panel URL must be a plain HTTPS origin. Providers must also place OniLink's embedded HTTP
  dashboard behind restricted HTTPS before entering a production panel credential.
- Pterodactyl requests use bounded timeouts, response sizes, and pagination, reject redirects, and
  retain the platform's normal certificate validation.

## Operator experience

- The dashboard explains the one-allocation model: Bedrock uses the tenant allocation over UDP and
  the tenant dashboard uses the same numeric port over TCP; the BDS server keeps its own allocation.
- The commercial-hosting guide and Wiki now lead with the main control plane. `tenantctl.py` remains
  available only as an offline recovery or scripted-automation fallback.
- The egg, version defaults, component manifests, examples, installation guides, and banners are
  aligned on `v0.1.5`.

## Verification

Regression coverage exercises a simulated Pterodactyl Application API end to end:

- customer, node, egg, and free-allocation discovery;
- isolated server creation and the zero-additional-allocation constraint;
- a standard-Base64 forwarding key containing 32 random bytes;
- handoff ZIP contents and matched trusted source CIDR;
- credential redaction and owner-only route enforcement;
- suspension state and tenant persistence across an OniLink restart.

The normal Java, Geyser, native, Python packaging, egg, formatter, ABI, and source-inventory gates
remain part of the release workflow.

## Upgrade

1. Back up `config.properties`, `dashboard/`, `allowlist.properties`, and forwarding key files.
2. Restart OniLink. An updater-enabled Pterodactyl server discovers the newest stable release,
   verifies `SHA256SUMS`, and replaces the JAR while preserving live configuration and dashboard
   data.
3. Reimport the v0.1.5 egg before provisioning new hosted instances so Pterodactyl has the current
   administrator-only variables and defaults. Existing runtime-only upgrades do not rewrite an egg
   definition already stored by Pterodactyl.
4. Sign in as the provider dashboard owner, open **Tenant Hosting**, save the panel connection, and
   follow the guided plan/customer/allocation workflow.

Existing backends, forwarding keys, allowlists, and tenant CLI-created servers remain valid.
