# OniLink 0.3.0-beta.8

OniLink `0.3.0-beta.8` fixes variable OniForward clock readings and expired tokens during slow or
retried backend connection setup. The fixed host-clock compensation introduced in beta 7 remains
available for separately hosted systems.

> [!IMPORTANT]
> The BDS 1.26.45.1 profiles remain candidates until the complete real-server startup, proxied
> login, verified XUID, disconnect, command, and shutdown matrix passes. Fresh token issuance does
> not relax the native profile gate.

## Fresh backend-login tokens

Earlier builds minted OniForward before opening the RakNet connection to BDS. Dialing, retries, and
backend protocol negotiation therefore consumed the token's short lifetime. Because the rejection
diagnostic compares issue time with backend receipt time, variable connection delay also looked
like a changing host-clock offset.

Beta 8 now:

- waits for the backend `NetworkSettings` response;
- mints a new signed OniForward token for that exact connection attempt;
- immediately embeds it in the backend Login packet and sends it once;
- mints another independent token for every retry or backend switch; and
- keeps the existing lifetime, two-second skew, signature, trusted-proxy, and replay policies.

## Upgrade and recovery

1. Update the OniLink container to the beta 8 `OniLink.jar`. This timing correction is in the proxy
   JAR; the beta 7 OniBridge shared library already supports the multi-hour fixed offset.
2. Keep `allowed_clock_skew_ms = 2000`.
3. Start with the largest observed immediate offset from the affected deployment:

   ```toml
   [forwarding]
   allowed_clock_skew_ms = 2000
   proxy_clock_offset_ms = 9922992
   ```

4. Restart OniBridge and OniLink, then attempt one join. If beta 8 reports a small residual time
   failure, replace the configured value once with that new immediate reading and restart
   OniBridge. Do not reuse readings produced by beta 7 or older JARs.

Existing forwarding secrets, key IDs, bridge IDs, backend names, player data, worlds, and control
plane accounts do not need migration.
