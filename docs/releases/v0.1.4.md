# OniLink 0.1.4

OniLink 0.1.4 makes additional BDS backends easier to install and introduces an isolated
Pterodactyl provisioning path for commercial hosting. The forwarding protocol and approved BDS
profile are unchanged.

## Faster backend setup

- **Add Backend** now asks for only the backend name, BDS allocation, and OniLink IP seen by BDS.
- Bridge and key labels are generated automatically, with overrides kept under advanced settings.
- One download contains the matched backend key, complete `onibridge.toml`, allocation summary,
  upload paths, restart order, and validation commands.
- The proxy configuration and protected proxy-side key are still installed atomically with
  revision, duplicate-route, and full configuration validation.
- The dashboard and documentation now explain that OniLink needs one primary allocation while each
  BDS server retains its own UDP allocation.

## Isolated tenant hosting

- `tools/tenantctl.py` creates one dedicated OniLink Pterodactyl server per customer through the
  Application API.
- Every generated tenant receives exactly one primary allocation, an additional-allocation limit of
  zero, separate configuration and dashboard storage, and tenant-specific forwarding keys.
- Provisioning is idempotent through `onilink-tenant-<tenant>` external IDs.
- Private plan and handoff files contain the generated dashboard setup code and matched default BDS
  configuration.
- `status`, `suspend`, and `unsuspend` commands provide a safe boundary for a verified external
  billing workflow. The tool intentionally exposes no public payment webhook and cannot delete
  customer data.
- The released egg adds a hidden administrator-only dashboard setup-code variable for automated
  tenant creation.
- The release bundle includes `tenantctl.py`, `tenantctl.example.json`, and
  `tenantctl-README.md`, all covered by `SHA256SUMS`.

## Maintenance

- Project-owned C++, Python, and dashboard sources now use checked-in formatter rules and CI style
  checks while generated and vendored boundaries remain explicit.
- Runtime templates and native parsing code were reorganized for maintainability without changing
  fail-closed forwarding behavior.
- Contributor documentation now records source ownership, formatting, testing, and privacy rules.

## Upgrade

1. Back up `config.properties`, `dashboard/`, `allowlist.properties`, and forwarding key files.
2. Restart OniLink. The stable updater downloads and verifies the v0.1.4 runtime while preserving
   active configuration and keys.
3. Reimport the v0.1.4 egg only when you need the new administrator-only tenant setup-code variable;
   the simplified backend page arrives with the JAR update.
4. Use **Add Backend** to create a setup ZIP for each new native backend.

The locked BDS version, Endstone version, OniForward protocol, and approved Linux profile did not
change. Existing matched forwarding keys remain valid.
