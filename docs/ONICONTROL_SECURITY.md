# OniControl security

OniControl is a separate trust domain from OniForward. Every backend uses a unique control key and a
different forwarding key. Java startup rejects reuse of the same configured secret source, and
native startup also compares the loaded bytes.

## ONICTL/1

Transport frames are a four-byte unsigned big-endian length followed by one strict UTF-8 JSON
envelope. Zero, oversized (default 262,144 bytes), invalid UTF-8/JSON, unknown required values, and
trailing input are rejected.

Requests sign this exact newline-delimited input:

```text
ONICTL/1
keyId
requestId
idempotencyKey
timestamp
nonce
bridgeId
backend
targetXuid
action
payload
```

`payload` is base64url-without-padding UTF-8 JSON. The signature is base64url-without-padding
HMAC-SHA256. Responses have their own fixed signed form including request ID, status, result,
timestamp, bridge/backend, and capability revision. Comparisons are constant time.

The native endpoint validates key, bridge, backend, source CIDR, target XUID, actor role, action
capability, clock skew, nonce, replay state, idempotency, frame size, connection count, and in-flight
limits before scheduling. Network workers never mutate BDS. Actions resolve the currently verified
XUID again and run on Endstone's primary thread.

The current native protocol does not carry a separately signed action deadline and does not yet
implement per-source/action/target rate buckets. Java enforces the typed request deadline before
and while waiting for the bridge, while native freshness is bounded by the signed timestamp and
clock-skew window. Treat native rate limiting and a signed deadline field as required hardening
before promoting the authoritative control path beyond `CANDIDATE`.

## Network policy

- Loopback is preferred for same-host deployment.
- Private TCP requires both sides' explicit private-network override and a narrow firewall rule.
- Public cleartext requires a separate dangerous override but is not generated by the dashboard.
- Cleartext HMAC authenticates integrity and identity; it does not provide confidentiality.
- The Java client implements TLS validation/pinning. The bundled native OniBridge artifact currently
  rejects TLS configuration because its reviewed TLS server transport is not implemented. Use a
  private tunnel for cross-host confidentiality; do not claim native TLS/mTLS support yet.

The control connection reconnects with bounded queues and jittered backoff. Its failure never stops
ordinary player forwarding.

## Rotation

Generate at least 32 random bytes, install the new separate file/environment value, change `keyId`
on both ends, restart the bridge then proxy, and confirm the signed capability document. ONICTL/1's
current native configuration accepts one active control key; use a brief maintenance window rather
than reusing an ID or forwarding key. Never include keys in support bundles or dashboard JSON.
